# QST-255 Report: Gemini Error Recovery and Non-Template Fallback

## Result

Partially implemented. Error taxonomy, bounded retry, Stable fallback routing, retry/manual statuses, and non-template failure behavior exist. Quest Planning V2 never returns a fixed Mission template when Gemini is unavailable.

User input remains in the client request and can be retried; no empty Quest or Mission is saved. Structured, successful early understanding, success-contract, and achievement-domain Pass outputs now have owner- and Quest-scoped 24-hour checkpoints. A later attempt can reuse them after renewed consent, operation-control, and schema checks. Tool-backed planning, including Google Search and live Quest context, always executes again. The checkpoint migrations were verified on the isolated Free validation project; full-route provider validation remains unverified.

## 2026-10-26 Follow-up

- Provider rate limits now reach the Quest UI as an actionable reason without showing raw provider errors or generating template Missions.
- Each Pass reservation key includes a digest of its structured input and active execution settings. A repaired Mission or Task plan therefore receives a distinct Critic reservation while an identical retry keeps the same identity.
- Tests cover input-sensitive reservation keys, the AI failure message, and HTTP retry status. This does not prove a complete hosted planning run.
- `202610260003_quest_planning_pass_checkpoints.sql` introduces private checkpoint storage with account/Quest ownership, expiry, cascade deletion, and no client grants. Completed early Passes can be reused across a later retry even if its request idempotency key changes; malformed outputs and revoked consent cannot be reused. Mission/Task candidates and Critic output are not cached before their domain quality gate. Internal request IDs and abuse hashes are removed from model payloads.
- Deno unit tests cover matching, owner and Quest isolation, consent denial, invalid schema, operation kill switch, and tool-backed no-cache behavior. DB RLS fixtures assert that authenticated clients cannot read or write checkpoints.
- The existing Supabase Free validation project (`tpynzjjqajpkzivgapfq`) received migrations `202610260003` and `202610260004` only; Beta was untouched. A hosted, rollback-only SQL fixture verified checkpoint insert/read, client privilege denial, and rejection of a different account bound to the owner's Quest. The SQL runner's nonzero behavior on an intentional read-only error was also checked. After rollback, fixture users and checkpoint rows both counted zero. This proves the hosted database contract, not a full Gemini planning retry.
- A hosted Deno test with a synthetic provider exercised the production checkpoint helper against two disposable accounts and Quests. An identical retry under a different idempotency key reused the first Pass without a second provider call; the second account did not receive that result. The fixtures were removed after the test. No Gemini request or paid service was used.
- A provider 429 now stops the same-request fallback instead of immediately calling another model. The bounded `Retry-After` value reaches the planning HTTP response and Quest screen; the retry control is disabled for that interval and becomes available again when it expires. The provider's raw quota message is not shown. Deno mock-provider tests (11), Flutter targeted tests (7), and full Flutter analysis passed. This is synthetic 429 coverage, not a live Gemini quota event.
- The authenticated Quest cooldown now persists only its expiry time in account- and Quest-scoped secure storage. Generation reloads it before any provider call, and the Quest screen restores the disabled retry control after app restart. Tests cover repository recreation, expiry, account isolation, restart suppression, a mid-request account switch, and the restored disabled button in a Quest detail widget; Flutter analysis passed. Unsupported local storage still falls back to active-session protection.
- A new database migration schedules hourly, bounded pruning of expired private Pass checkpoints and removes the unbounded cleanup trigger from each write. The rollback-only DB fixture verifies that expired output is removed, live output remains, the client cannot invoke cleanup, and the scheduled job is active. The local-db CI check passed; neither Beta nor the isolated validation project has received this migration yet.
