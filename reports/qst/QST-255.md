# QST-255 Report: Gemini Error Recovery and Non-Template Fallback

## Result

Partially implemented. Error taxonomy, bounded retry, Stable fallback routing, retry/manual statuses, and non-template failure behavior exist. Quest Planning V2 never returns a fixed Mission template when Gemini is unavailable.

User input remains in the client request and can be retried; no empty Quest or Mission is saved. Structured, successful early understanding, success-contract, and achievement-domain Pass outputs now have owner- and Quest-scoped 24-hour checkpoints. A later attempt can reuse them after renewed consent, operation-control, and schema checks. Tool-backed planning, including Google Search and live Quest context, always executes again. The new migration is local only; hosted checkpoint behavior and full-route provider validation remain unverified.

## 2026-10-26 Follow-up

- Provider rate limits now reach the Quest UI as an actionable reason without showing raw provider errors or generating template Missions.
- Each Pass reservation key includes a digest of its structured input and active execution settings. A repaired Mission or Task plan therefore receives a distinct Critic reservation while an identical retry keeps the same identity.
- Tests cover input-sensitive reservation keys, the AI failure message, and HTTP retry status. This does not prove a complete hosted planning run.
- `202610260003_quest_planning_pass_checkpoints.sql` introduces private checkpoint storage with account/Quest ownership, expiry, cascade deletion, and no client grants. Completed early Passes can be reused across a later retry even if its request idempotency key changes; malformed outputs and revoked consent cannot be reused. Mission/Task candidates and Critic output are not cached before their domain quality gate. Internal request IDs and abuse hashes are removed from model payloads.
- Deno unit tests cover matching, owner and Quest isolation, consent denial, invalid schema, operation kill switch, and tool-backed no-cache behavior. DB RLS fixtures assert that authenticated clients cannot read or write checkpoints.

## Remaining

- Rehearse and deploy the checkpoint migration to an isolated Supabase project, then prove persisted retry reuse and account isolation against the hosted database. Beta remains unchanged until its older migration gap is resolved.
- Add time-driven retention cleanup for checkpoints on inactive accounts; current cleanup is opportunistic on a later checkpoint write and cascade deletion on account/Quest removal.
- Verify 429 cooldown and the full Quest-to-Mission-to-Task preview, Critic, repair, approval, and rollback against a real provider without paid usage.
