# QST-169 Authentication Lifecycle and Login Hardening

## Status

**Local implementation complete; Supabase Beta activation pending**

## Goal

初回のユーザー作成からログイン、モバイルの安全なセッション復元、Webの都度ログイン、パスワード再設定、連続失敗時の一時ロックまでを一貫した認証ライフサイクルとして定義・実装する。

## Product Decisions

- 初回はログインID、メールアドレス、パスワード、呼び名を登録し、メール確認後にログインする。登録直後の自動ログインは行わない。
- モバイルはSupabaseのアクセストークンと更新トークンをOSの安全な保存領域へ保持し、有効なセッションを次回起動時に復元する。
- Webは永続ストレージを使わず、ページ再読み込み、タブ終了、再訪問後にログインを要求する。
- ログイン画面はログインIDまたは登録メールアドレスを受け付ける。対応関係を公開Profileへ保存しない。
- 15分以内に10回失敗したアカウントは30分間、新しいログインを拒否する。既存セッションは攻撃者による強制ログアウトを避けるため維持する。
- パスワード再設定はアカウント有無を判別できない共通文言を返し、完了時にロックを解除する。

## Implementation

- `auth_login_accounts`、所有者非公開のログイン識別子、失敗回数、ロック期限を追加した。
- `auth-login` Edge FunctionでログインID解決、パスワード認証、失敗記録、ロック判定、汎用エラー、4KB body制限、Origin制限を実装した。
- 対応プラン向けPassword Verification Hookを用意し、公開Auth APIへ直接アクセスする迂回ログインもロックできる構成にした。
- `flutter_secure_storage`を使うモバイル用Supabase session storageと、`EmptyLocalStorage`を使うWeb方針を実装した。
- 登録、ログイン、パスワード再設定依頼、新パスワード設定、Splash自動復帰を画面とRouterへ接続した。
- Android/iOSに`com.questra.questra://login-callback`を登録し、Webの`/#/reset-password`と分離した。
- 認証仕様を`docs/product/authentication_spec_v1.md`へ記録した。

## Security Notes

- パスワード、Service Role Key、アクセストークン、更新トークンはログへ出さず、クライアント成果物へ埋め込まない。
- ログイン失敗文はID、メール、ロック状態の正否を区別しない。
- 認証応答は`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`を付与する。
- Password Verification Hookを利用できないプランでは、Questra独自の10回ロックは公式クライアント経路で強制される。直接Auth APIへの完全強制はHook対応プランで有効化する。
