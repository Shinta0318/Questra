# QST-540 Signup Confirmation Resend and Recovery UX

Status: In Progress / local_partial

## User problem

After signup, the login notice told users to open a confirmation email but offered password reset as the remedy for non-delivery. Reset requires email delivery too. A returning user had no confirmation-resend path.

## Implementation

- Added a public confirmation-help route from login. The form validates the registered email, offers a non-automatic correction for common domain typos, and explains that resending cannot change a mistyped signup address.
- Connected builds use Supabase Auth `resend(type: OtpType.signup)` with the QST-539 confirmation redirect. The response does not claim inbox receipt or reveal whether an account exists. A successful request disables immediate repeats for 60 seconds; failure preserves the form for retry.
- Local mock previews display that email cannot be sent and do not show the resend command. Signup notice no longer points to password reset for an undelivered confirmation message.
- No live email was requested and no external Auth setting was changed.

## Local verification

- `flutter test test/qst_540_confirmation_resend_test.dart --no-pub`: 6 tests passed for public route, compact login navigation, mock honesty, large-text reachability, validation/typo correction/cooldown, and failed request behavior.
- The broader QST-538-540 and auth-contract suite passed 23 tests before the large-text case was added; it was rerun separately afterward.
- Full `flutter analyze --no-pub`: no issues. Backlog SSOT gate: PASS (486 QST IDs). External Beta decision verifier: `no_go` as required.
- The connected Flutter Web preview at `http://127.0.0.1:5282/#/confirm-email-help` rendered the new screen on desktop and at a 390x844 viewport. The heading, explanation, email input, resend command, and return link were visible without overlap. The preview used the hosted Beta Supabase public client key; its preflight Auth and Data API probes passed. No resend command was activated, so this is not delivery evidence.

## Remaining acceptance and risk

1. After QST-538 custom SMTP and QST-539 redirect allowlist are configured, validate actual resend receipt and callback on Web and Android using dedicated accounts. Until then, delivery remains unproven and external Beta is NO-GO.
2. Confirm server-side rate limits and abuse controls. The 60-second UI cooldown improves ergonomics but is not an anti-abuse security boundary.
3. Test large text, Japanese IME, screen reader announcement, and real small-device layout. A valid-format address entered for a different account is intentionally not disclosed in the response.

Rollback: Remove the help route and resend action without changing account data; do not disable email confirmation to compensate for delivery or redirect failures.
