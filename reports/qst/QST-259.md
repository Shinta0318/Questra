- Mission Granularity Classifierを追加し、`quest / mission / task / too_abstract / duplicate`を区別する契約を実装した。
- Success Contractの必須条件を確認するCoverage Analysisを追加した。
- Criticを10評価軸と明示的な最低点へ強化した。1項目でも閾値未満の候補は表示前に不合格となる。
- 不合格候補と構造・Coverage不足だけを最大2回Repairし、合格候補を維持するPipelineへ更新した。
- サーバー側Semantic ValidatorへTask粒度、Quest言い換え、重複、Success Contract未対応の検出を追加した。
- Flutterの本番生成経路を旧`arc-quest-guide`から`quest-planning-v2`へ切り替えた。
- Gemini障害時に本番で固定Missionテンプレートへ退避せず、入力を保った再試行メッセージを返すようにした。
- Mission候補画面へ中間成果、完了条件、必要理由、必須/任意、想定Task数、前提Mission、並行可否を表示した。
- ユーザー承認時だけ`approve_quest_plan_preview`を呼び、Route・Mission・初期Taskを一括保存するようにした。
- `mission_plan_drafts`、`mission_candidates`、`mission_plan_feedback_events`を追加し、正式Missionと候補を分離した。
- 採用、編集、削除の候補フィードバックを記録するRPCと、plan承認状態を同一トランザクション内で同期するtriggerを追加した。
- 既存の進捗イベントRPCが存在しない`missions.owner_id`を参照していた問題を、Quest joinによる所有者確認へ修正した。

## 2026-10-28 Approval Feedback Follow-up

- The Flutter client previously recorded each Mission candidate as accepted, edited, or deleted before the route approval RPC succeeded. A failed or conflicting approval could therefore leave adoption events and candidate decisions for a route that was never committed.
- Candidate feedback now runs only after the server returns `approved`. The database trigger still records `plan_approved` within the approval transaction; candidate-level feedback remains best-effort and cannot roll back an approved route.
- HTTP-mocked Flutter tests verify that a conflicting approval emits no candidate feedback and that successful approval precedes the feedback RPC. The focused test file and `flutter analyze --no-pub` passed. This change is local only; hosted transaction and analytics verification are still required.

## 2026-10-28 Pending Preview Rejection Follow-up

- A request to reconsider the entire route could previously reuse the same planning attempt and replay the unchanged preview. The review screen now offers an explicit "この案を見送る" action. "全体構成を見直す" rejects the pending preview before starting a new attempt.
- The authenticated Edge endpoint updates only a pending preview matching the owner, preview ID, and approval token. The existing database trigger marks its draft rejected and records the rejection. A conflict or storage failure leaves the preview visible and retains the local attempt key for retry.
- HTTP-mocked Flutter tests cover rejection success and conflict; a widget test covers the preview remaining visible after rejection failure and disappearing after success. The local PostgREST fake covers owner/token/status constraints and storage failure. No Gemini call or Beta project mutation was made for this follow-up.
- Hosted trigger execution, Web/Android interaction, and end-to-end rejection/replanning remain unverified. They are release gates, not evidence of completion.
