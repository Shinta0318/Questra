# QST-343 Report: Exact-SHA Supabase Deployment and RLS Evidence Gate

## Status

In progress. Static preflight hardening is complete, but hosted Supabase deployment and two-account RLS evidence are not yet complete for the current candidate SHA.

## Objective

Bind the Flutter app artifact, Supabase migrations, Edge Functions, RLS behavior, and Gemini route to one exact candidate SHA before treating the Beta candidate as deployable.

## Changes

- Expanded the Supabase Beta bootstrap Function inventory from 9 to all 12 configured Edge Functions.
- Added preflight checks that every required Function has an `index.ts` source and a `supabase/config.toml` block.
- Added a guard that fails if a new Edge Function directory exists but is not listed in the bootstrap required inventory.
- Added `-Apply` guardrails requiring a resolvable 40-character Git SHA and a clean worktree before hosted deployment evidence can be written as verified.
- Updated the static verifier to cover all configured Edge Functions, including `quest-planning-v2`, `quest-planning-tools`, and `process-data-rights-requests`.
- Updated the Supabase Beta bootstrap runbook from stale 6/9 Function language to 12 configured Functions.
- Marked `process-data-rights-requests` in `docs/qst/BETA_SUPABASE_PROJECT.yaml` as `local_pending_deployment` instead of silently omitting it.
- Regenerated `docs/qst/BETA_CANDIDATE.yaml` as a non-distribution-ready draft bound to the current local inventory.
- Added candidate manifest fields for Edge Function names, Supabase evidence commit, RLS evidence commit, and SHA match status.
- Strengthened candidate verification so an approved candidate requires complete external evidence bound to the same SHA.
