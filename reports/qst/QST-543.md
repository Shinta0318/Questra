# QST-543 Direct AI Function User Boundary

Status: In Progress / local_partial

## Finding

- 2026-10-07 Dashboard read-only check: Questra Beta is healthy, but the seven direct Arc/Gemini functions were deployed about two months earlier. The `arc-quest-guide` setting has legacy `Verify JWT` enabled. Supabase documents that an API key can pass this platform check; it does not prove a signed-in user. The local handlers previously lacked a user check. The connected-preview runbook also records a 2026-10-05 public-key-only Gemini response.
- Hosted, non-generating probe with only the publishable key: `/auth/v1/user` returned 401, while an empty Arc chat request returned HTTP 200 with `source_type=arc_chat_fallback`. Malformed JSON POSTs reached all seven deployed function handlers: six returned 400 and `moderate-quest-intent` returned 200, rather than 401. This proves their current hosted entry boundary is not a signed-in user check. It does not by itself prove a fresh nonempty Gemini call; the earlier runbook is the evidence for that.
- A caller with only a public key could reach paid AI work in the local implementation. Existing Quest Planning v2, Planning Tools, and Mission Research have their own user checks; the finding concerns the seven direct handlers.

## Local implementation

- Added a shared Auth `/auth/v1/user` check before parsing or AI/search work. Missing, publishable-only, rejected, malformed, and failed Auth requests return `401` without invoking the provider.
- Applied the boundary to Arc Chat, Arc Quest Guide, Generate Arc Advice, Generate Mission, Generate Quest Guides, Generate Star Map, and Moderate Quest Intent.
- Passed the verified user ID into each AI call and made the shared text provider fail closed when that ID is absent. Usage events can now be attributed to the authenticated user for these calls.
- No hosted settings, secrets, account data, or production function deployments were changed.

## Verification

- `node --test supabase/functions/_shared/ai_auth.test.mjs`: 5 tests passed. They exercise missing/API-key-only requests, Auth validation failures, a valid user, the provider guard, and anonymous/signed-in paths through all seven handlers without a real model call.
- `node --test tools/qst/verify_hosted_ai_auth_boundary.test.mjs`: probe contract tests passed. The matching command `node tools/qst/verify_hosted_ai_auth_boundary.mjs` requires `SUPABASE_URL` and `SUPABASE_ANON_KEY` from the local environment, prints only function names and HTTP statuses, and must return 401 for every function after deployment. The current deployed version is expected to fail this gate.
- The hosted probe was run on 2026-10-07 against the currently deployed Beta project, using only the publishable key and invalid JSON. It failed as expected: `arc-chat`, `arc-quest-guide`, `generate-arc-advice`, `generate-mission`, `generate-quest-guides`, and `generate-star-map` returned 400; `moderate-quest-intent` returned 200. No secret, user account, personal content, or valid AI prompt was used. This is a pre-deployment baseline, not a successful security gate.
- `node --test` for both local test files passed 7/7. `dart tools/qst/verify_backlog_ssot.dart` passed with 489 IDs. No Deno CLI typecheck or hosted signed-in happy-path test was run.
- Node loaded all seven TypeScript handler modules and the legacy adapter. Deno typecheck, actual Supabase Auth round trips, hosted function deployments, and Gemini requests remain unverified.
- 2026-10-07 read-only Dashboard check: custom SMTP is off; Site URL is `http://localhost:3000`; Redirect URLs are empty. In the preceding 24-hour Auth logs, `mail.send` for confirmation and `POST /signup` appear, along with `Email not confirmed` and invalid-login responses. `mail.send` is not inbox-delivery proof. No address or token is copied into this report.
