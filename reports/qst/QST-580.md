# QST-580 Server-Verified One-Time Consent at the Gemini Boundary

Status: In Progress (local verification only)

## Finding

The signup SQL trigger writes one versioned `legal_acceptances` row, and the Flutter router sends an account with a current server record directly to Home. However, the shared Gemini provider previously had no server-side consent check. A direct authenticated Edge Function call could skip the Flutter route guard. Also, after a successful legacy one-time acceptance, the client updated `legalAcceptanceCurrent` but did not reset a prior unavailable-check flag in the same profile.

## Change

- Add `has_current_ai_legal_acceptance(uuid)`, executable only by `service_role`. It checks the active JP policy and an exact-version, age-confirmed server acceptance.
- Check this RPC before any Gemini request, model selection, or AI budget reservation. A missing record returns `consent_required`; an unavailable lookup fails closed. No signup metadata is used as proof.
- Bind the planning provider's `userId` to the Function Calling tool context before attribution, Gemini, or tool execution. Mismatched or malformed identities fail without side effects.
- Inspected the production callers: `quest-planning-v2` derives its user ID from the bearer session, and the direct AI and grounded-search callers pass their authenticated user ID to the shared adapter. The new orchestrator check prevents a future caller from mixing two identities.
- Set the client's acceptance-check state to available after the RPC succeeds and the new row has been read back, avoiding a second consent prompt in that session.
- Extend the rolled-back SQL contract to cover new-signup records, an intentionally missing legacy record, explicit legacy confirmation, policy version changes, and RPC privileges. Update the isolated DB workflow's expected migration head.
- Keep the Beta project manifest's *local* migration head current. Remote deployment is not claimed.

## Boundary and Release Decision

Consent is a one-time user action, not a checkbox requested at every login. The app may still read the current server policy and recorded acceptance on sign-in, and the server checks before sending content to Gemini. The existing legacy recovery path needs one explicit action only when no server record exists; user-editable signup metadata cannot silently replace that record. An unavailable lookup must not be treated as a new consent request or a successful acceptance.

The observed Beta remote migration head predates the legal tables and trigger. This code alone cannot repair a Hosted account whose signup occurred before the trigger was deployed. Keep External Beta **NO-GO** until the complete migration chain is rehearsed and deployed in order, with a recovery point, and a disposable account proves signup, email confirmation, subsequent login without a second prompt, and Gemini access/denial. Do not deploy only this latest migration against the old remote schema.
