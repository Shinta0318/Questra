# QST-581 Explicit Consent Failure Across AI Entry Points

Status: In Progress (local verification only)

## Finding

Arc Chat returned a distinct legal-consent failure, but other AI Edge entrypoints could turn the same denial into an ordinary generation failure or a local fallback. Users then had no explanation that their content had not been sent. The shared Gemini adapter from QST-580 already failed closed; this QST makes the HTTP and UI boundary explicit across the remaining callers.

## Local Change

- Apply the authenticated server-record check to Arc quest intent, guide and Mission regeneration, planning and Task expansion, moderation, Mission research, advice, Mission generation, guide generation, and Star Map generation.
- Keep deterministic safety responses before the AI gate, cached research readable without a new AI call, and preview approval separate from AI planning. A missing acceptance returns `consent_required` (403); a failed lookup returns `consent_check_unavailable` (503).
- Map the two errors to distinct Japanese messages in the Flutter Quest intent, route, Task, Mission regeneration, and research paths. Inputs remain in their current editors. The older advice refresh no longer completes with a misleading local AI replacement on a consent failure.
- Keep the route error text free of Dart's `Bad state:` prefix and show it without the prior two-line truncation; Mission regeneration notifications use the same plain-language treatment.
- Update the Hosted auth probe for the two additional AI endpoints and for a declared signed-in consent state. A malformed Arc Chat request returns 400 for a consented fixture and 403 for an explicitly missing-consent fixture; 503 never passes. The malformed probe does not prove the legal gate of every other endpoint, which still needs a Hosted valid-request denial test.
- Add focused server and Flutter tests for the error contract and entrypoint guard coverage.
- Guard direct `quest-planning-tools` requests before any tool can read Quest or Arc Memory data. Preserve the existing user/Quest authorization and tool allowlist after the consent check.
- Let the Flutter safety service surface explicit consent denial or lookup failure instead of silently replacing it with the local allow result. Local blocks and distress reframes still run before any remote call; ordinary remote failures retain the existing local fallback.
- Follow-up: Arc Chat now shows the dedicated consent error even when it originates from the preliminary safety request, and records the distinct degraded reason. A generic Arc error had previously hidden that path.

## Hosted Probe Use

Supply `SUPABASE_URL` and the publishable `SUPABASE_ANON_KEY`. With a disposable signed-in account, supply `SUPABASE_USER_JWT` only in the local environment. The probe expects a current legal acceptance by default; set `SUPABASE_USER_CONSENT_EXPECTED=missing` only for a deliberately unaccepted fixture. It sends malformed JSON, not personal conversation content, and prints only function names and status codes. Never put tokens in reports or logs.

## Release Boundary

This is local code only. The observed Beta remote migration head predates the legal tables and trigger. Do not deploy only the newest migration or infer consent from editable signup metadata. Hosted migration rehearsal/deployment, disposable account signup and login, a second login without another consent prompt, two-account RLS, AI denial and success, and a simulated consent-lookup outage are still required. External Beta remains **NO-GO** until those are proved.
