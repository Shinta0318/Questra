# QST-400 Provider-backed 200-case Planning and Safety Evaluation

## Result

Implementation validation pending. QST-402 found local execution and evidence-quality issues; this is not ready merely by supplying external credentials or approvals.

## Findings Fixed

- Cost evidence previously accepted zero token prices, which could report a misleading zero-dollar run.
- Version consistency checked prompt/schema data but did not bind model and thinking-level combinations.
- Safety endpoint fallback responses could be counted as successful evidence.
- Human evaluation was described but not connected to the release gate.
- A single free evaluation account could not execute 200 planning cases under the production quota, and the prior default interval could exceed the network abuse limit.

## Changes

- Provider passes expose a thinking-level field alongside model and model family. QST-402 found the legacy/error paths can report the requested rather than executed level; actual execution attribution remains unverified.
- The runner requires an explicit pricing version and non-zero input/output token prices.
- Every result is bound to one candidate SHA and run ID; planning records model, thinking, prompt, schema, usage, cost, latency, and trace identifiers.
- Safety accepts deterministic policy decisions and Gemini decisions but rejects fallback/error sources.
- Human review requires at least 40 planning cases across 10 categories and 10 personas plus all 10 safety cases.
- The hosted run uses eight ephemeral accounts with 25 planning cases each and a minimum 2.1-second interval; all accounts must be deleted before results are written.
- Automated and human evidence are hash-bound in `PROVIDER_EVAL_RUN.yaml`.
- The runner now extracts the actual `preview.routeMissionPlan.missions` contract,
  separate Task content, success contract, strategy, Critic verdicts, and source references.
  Review material is allowlisted; approval tokens and raw provider responses are excluded.
- Repeated Critic passes after targeted repair are permitted, but the final verdict must
  pass for each Mission and the latest final validation must complete.
- Human review is bound to the result file and both committed corpus hashes. The strict
  verifier recomputes per-case scores and coverage instead of trusting aggregate flags.
- A preselected category/persona sample is mandatory. Additional cases are allowed, but
  cannot replace required cases or dilute a failing fixed-sample score. Both the fixed
  sample and full reviewed set must achieve 85%; all safety cases must pass.
- `prepare_provider_human_review.dart` creates an unscored template and inspectable
  material under ignored artifacts. See `docs/qst/PROVIDER_HUMAN_REVIEW.md`.

## Current Blockers

- Eight account shards do not establish sufficient quota: each provider pass calls `reserve_ai_usage_budget`, while the free Quest Planning policy allows 30 reservations per month. A bounded, explicitly authorized evaluation allocation and resumable runner are still needed; adding more accounts is not an acceptable substitute.
- Model/thinking fingerprints must distinguish pinned configuration from the subset of passes actually executed, and pricing must match the selected model.
- Inspectable output and score recomputation are implemented and fixture-tested. A real
  provider run and genuine independent human review are still required.
- Some automated metrics remain proxies: keyword hits do not establish Mission specificity
  or non-template quality. Dimension-level Critic evidence and human calibration must be
  reviewed before the quality thresholds can establish a release decision.
- A clean candidate SHA does not yet exist.
- Hosted migrations and Edge Functions are not deployed from that candidate.
- The 200+10 provider run and human scoring have not been executed.
