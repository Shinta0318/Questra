# QST-538 Signup Email Typo Confirmation and Delivery Release Gate

Status: In Progress / local_partial

## User problem and scope

- A syntactically valid but mistyped email address can create a pending account whose confirmation message the intended user cannot receive. The existing format validator cannot detect a domain typo.
- QST-169 covers the authentication lifecycle and QST-414 covers plain-language entry. This QST adds a narrow, non-blocking typo suggestion and a distinct external mail-delivery release check. It does not replace those QSTs or add a mail provider to the app.

## Implementation

- Signup now explains that the address is the confirmation-mail destination. For a short list of known typo domains, it offers an explicit correction and asks for confirmation before submitting the original address. It never rewrites the address automatically and does not reject other valid domains.
- The external Beta Go/No-Go evaluator now includes `auth_email_delivery`. A clean candidate must have redacted evidence for custom SMTP, receipt of confirmation and recovery messages, completed confirmation, and successful first login. Missing or stale evidence remains blocked.
- `BETA_EMAIL_DELIVERY_EVIDENCE.yaml` is intentionally `unverified`. As observed in the Beta Dashboard on 2026-10-06, email confirmation was enabled while custom SMTP was disabled. Auth logs recorded mail-send events but did not prove inbox delivery. No recipient address is included here.
- Rechecked the live Beta Dashboard on 2026-10-06: the SMTP toggle remained off, Confirm email remained on, and the intended-domain test account showed a confirmation-send timestamp but no confirmation or sign-in timestamp. The recent Auth log contained `/signup` success and `Mail.send`, followed by a failed `/token` request. This is not evidence of inbox receipt; the token error alone does not distinguish an unconfirmed address from incorrect credentials.

## Remaining acceptance

1. Configure a production-suitable custom SMTP provider in Beta with sender-domain verification, rate limits, and abuse protection. Supabase's default sender is restricted to pre-authorized project-team addresses and is not a release solution; see https://supabase.com/docs/guides/auth/auth-smtp.
2. On one clean candidate SHA, use dedicated test accounts to verify confirmation email receipt, link/deep-link completion, login, password-reset email receipt, error recovery, and cleanup. Record only sanitized receipt evidence.
3. Review the signup flow at small Web/Android widths, large text, Japanese IME, and screen reader settings. Confirm that the correction suggestion and dialog are reachable and understandable.

Rollback: The typo suggestion can be removed without changing account data. Do not disable email confirmation to work around SMTP delivery failure; keep external Beta blocked until delivery is proven.
