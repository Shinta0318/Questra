## Finding

The login profile check previously queried only an acceptance matching the app's compiled policy version. It did not compare that version with the active server policy. If the server policy advanced first, a stale app could treat an older acceptance as current. The signup preflight already read the active policy but reported a version mismatch as generic service unavailability. A stale app must not present the old consent form or silently enter Home.

## Local change

- Classify an active server policy as current, unavailable, or requiring an app update. A missing policy or failed lookup is still an unavailable service, not missing user consent.
- Profile loading first checks the active JP policy. Only when the policy matches the app's version does it read the user's exact-version server acceptance. A mismatched policy blocks protected routes and presents an update message without checkboxes or a misleading second consent prompt.
- The route guard also rejects a contradictory cached profile that claims acceptance while carrying a policy-update or lookup-unavailable state.
- Signup rejects a mismatched active policy before creating an Auth account and explains that Questra must be updated. The existing fail-closed handling of an unavailable policy remains.
- An already recorded acceptance on a matching policy still routes directly past the consent page. Signup metadata remains display-only and never substitutes for a server acceptance.
