# QST-511 Owner-scoped Task Mutation Serialization

## Summary

Task offline queueはownerごとに1件を保持する。従来は保存が重なると後続操作が
先行操作のqueue記録を上書きし、先行失敗後の再試行情報を失う可能性があった。
Task Controllerでowner別に保存・並び替え・再試行・破棄を直列化した。

## Changes

- owner別の操作tailで同一ownerのTask mutationを順番に処理する。
- 後続の通常保存は先行操作が完了し、再試行待ちがない場合だけ開始する。
- 先行操作が失敗した場合、pending queueを維持し後続保存はfail closedする。
- 再試行と破棄は実行時に最新pendingを再確認し、古いUI操作で上書きしない。
- 別ownerの操作は旧ownerの通信完了を待たない。QST-510のowner境界を維持する。

## Master Spec Alignment

ユーザーの挑戦データを失わず、保存失敗時には再試行可能な状態を維持する。
owner境界を越えたTask表示・更新を許さない。

## Residual Risk

- 物理端末での連打、アプリ強制終了、実Supabaseの二アカウント同時操作は未実証。
- owner別queueは1件なので、失敗中の新規操作は自動的には保留しない。
  利用者が再試行または破棄してから操作し直す必要がある。
- 保存待ちの間に別操作が古いTask snapshotから作られた場合、queue順序は守られても
  フィールド値を上書きし得る。次QSTでstale snapshotを拒否または再評価する。
- Task以外のQuest、Mission、Trail mutationは本QSTの直列化対象外。
