# QST-539 Auth Email Redirect Contract and External Beta Gate

Status: In Progress / local_partial

## Evidence and problem

- The hosted Questra Beta Dashboard was inspected on 2026-10-06. Its Auth Site URL was the default `http://localhost:3000` and its Redirect URLs list was empty. The preview runs on a different local port; a confirmation or recovery email could therefore return to the wrong place even if delivered.
- `signUp` had no explicit confirmation redirect. Password recovery already supplied a redirect, but the hosted project did not allowlist it. No link was clicked, and no recipient address, token, or credential is recorded here.

## Local implementation

- Signup now passes an explicit confirmation redirect: the current Web origin's `/#/login` or the existing native auth callback. Recovery uses the same central redirect contract for `/#/reset-password` or the native callback.
- The external Beta decision has a separate `auth_redirects` gate. It requires an approved HTTPS Site URL, exact Web and native allowlist entries, candidate-bound clean-tree evidence, successful link returns for confirmation and recovery on both platforms, and operator approval.
- `BETA_AUTH_REDIRECT_EVIDENCE.json` remains `unverified`, accurately reflecting the hosted settings. No hosted Auth setting was changed.

## Verification

- `flutter test test/qst_539_auth_redirect_gate_test.dart --no-pub`: 3 tests passed. They cover redirect generation, explicit signup wiring, and rejection of localhost, missing or extra allowlist entries, stale SHA, missing link evidence, and unsafe evidence path.
- Full `flutter analyze --no-pub`: no issues. The QST-539/538 and related auth suite passed 18 tests before the extra-allowlist assertion was added; that assertion is rerun below.
- External Beta decision generator and verifier passed with `no_go` and 14 blocked gates. Backlog SSOT gate passed with 485 QST IDs.

## Remaining acceptance

1. Configure a real HTTPS Site URL and exact allowlisted Web confirmation, Web recovery, and native callback URLs in hosted Beta. Do not use wildcards or disable email confirmation to bypass the issue.
2. After SMTP is configured, use dedicated test accounts on one clean candidate to verify actual confirmation and recovery link round-trips on Web and mobile. Record redacted evidence only.
3. Verify that confirmation does not silently bypass the product's required first explicit login and that reset links reach the password form. Keep external Beta NO-GO until both QST-538 delivery and this redirect gate pass.

Rollback: Remove the explicit signup redirect only if a tested, approved Site URL safely replaces it. Keep the redirect gate blocked whenever hosted settings or link behavior are unverified.
