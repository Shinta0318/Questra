# QST-515 Route Mutation Persistence Acknowledgement

## Summary

ローカル航路承認ではQuest・Missionのstate変更後に保存を非同期で開始していたため、Repository保存失敗でも提案が承認済みになる可能性があった。通常画面のoptimistic操作は維持し、航路承認専用に段階適用・await保存・補償復旧の境界を追加した。

## Changes

- Questに航路変更用のstate段階適用、await保存、snapshot復旧APIを追加した。
- Missionの航路操作は承認処理中だけ自動保存を抑止できる。
- 変更後のMission一式とremoved状態をawait保存し、失敗を承認処理へ返す。
- 復旧時に新規Missionを物理削除せず`routeState: removed`で保持し、元snapshotを再保存する。
- 航路snapshotへMissionタイトル、説明、完了条件、成果、期間、難易度、情報要件、信頼度を追加した。
- QuestまたはMission保存が失敗した場合、提案を確定せずQST-514の補償復旧へ進む。

## Master Spec Alignment

Arcの航路提案は、画面上の変更だけでなくユーザー所有データの保存が確認された後に確定する。保存失敗を成功として見せず、削除より可逆な状態保持を優先する。

## Security and Data Safety

- 復旧対象外のMissionは物理削除せず、非表示状態として保持する。
- owner変更後の保存結果は既存Controllerのowner確認に従う。
- Supabase接続時の航路適用は既存RPCを使用し、クライアント側の段階保存経路へ入らない。

## Residual Risk

- ローカル補償は複数Repositoryにまたがるため、プロセス強制終了時の完全なACID transactionではない。
- 復旧保存そのものが失敗した場合は手動確認警告を保持するが、自動再試行はしない。
- 実SupabaseへのRPC配備、二アカウントRLS、物理端末の強制終了は未検証。
