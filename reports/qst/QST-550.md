## Evidence and correction

QST-547 recorded a read-only Dashboard observation that the intended account was confirmed and not locked. Its login-account lookup succeeded, but the downstream Supabase password grant returned `invalid_credentials`. Therefore missing email confirmation is **not** the diagnosed reason for that account's current failure. Password reset completion and a successful user-entered login remain unverified. Do not record credentials or infer the password from logs.

The current hosted project requires email confirmation. A synthetic public-key probe found Auth settings 200, `auth-login` 401/`invalid_credentials`, the login-account table present but anonymous access denied (401/42501), and the Auth password endpoint accepting the public key while rejecting a synthetic invalid credential (400/`invalid_credentials`). These checks prove reachability, not an actual account sign-in.

## Local implementation

- Flutter classifies Edge Function 401/`invalid_credentials`, 429, and transport/relay/server failures separately. Server or network failures no longer look like a bad login ID/password. Account-existence and confirmation state remain private.
- The local `auth-login` handler returns 503 when its account-table query itself fails, instead of treating the result as an unknown account. The existing lockout path is unchanged.
- QST-548 added a Japanese-input check for the shared light field, in addition to explicit contrast checks for the auth fields.
