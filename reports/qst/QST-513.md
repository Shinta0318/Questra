# QST-513 Route Approval Task Failure Propagation

## Summary

ローカル航路承認ではRepositoryが提案を承認済みにした後、Task変更の`false`を確認せず成功表示へ進む経路があった。Task変更の失敗を例外へ変換し、承認成功を出さず、提案を最新状態での再確認へ戻すようにした。

## Changes

- Taskの日程変更、並び替え、分割開始の結果を必ず確認する。
- 対象Taskがない、完了済み、payload不足の場合も暗黙に成功扱いしない。
- 失敗時は現在のQuest・Mission・Task snapshotを保存し、提案を`stale`へ戻す。
- 途中まで状態が変わった場合は「一部の変更が反映された可能性」を明示する。
- 変更が未選択の場合、Quest詳細と航路画面の双方で成功通知を出さない。

## Validation

- QST-513、512、265および航路再計画の集中回帰: 16件PASS。
- 追加テスト3件: Task変更失敗、Quest変更後のTask失敗、正常承認を検証。
- アプリ全体の`flutter analyze --no-pub`: PASS、警告0件。
- `git diff --check`: whitespace errorなし。改行コードの変換警告のみ。
- `dart run tools/qst/verify_backlog_ssot.dart`: PASS（460 IDs）。

## Master Spec Alignment

Arcはユーザーの航路を勝手に確定せず、承認した内容が実際に反映された場合だけ成功として扱う。更新競合や部分反映を隠さず、ユーザーが最新の航路を確認できる状態を維持する。

## Residual Risk

- 本QSTは失敗伝播と誤った成功表示を防ぐが、ローカル経路の一部反映を自動ロールバックしない。
- Quest・Mission controllerの一部保存は非同期で、ローカル複数変更はDB transactionではない。
- Supabase接続時は既存RPCの原子性に依存し、実プロジェクトへの配備・二アカウント検証は本QSTの証跡外。
- ローカルの補償復旧はQST-514で扱う。
