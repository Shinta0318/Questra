- Source: QST-567 QR-36. The Beta Supabase organization displayed Free plan usage in the Dashboard.
- Official basis (checked 2026-10-16): [Auth Hooks plan table](https://supabase.com/docs/guides/auth/auth-hooks) lists Custom Access Token on Free/Pro and Password Verification Attempt on Teams/Enterprise. [Custom Access Token Hook](https://supabase.com/docs/guides/auth/auth-hooks/custom-access-token-hook) lists `password`, `recovery`, and `token_refresh` as authentication methods.

## Finding

The local Auth config enabled a hook unavailable on the Beta organization's Free plan. The SQL invoker hook read `auth_login_accounts` with no `supabase_auth_admin` RLS policy; table grants alone do not satisfy the Auth Hooks security model. The prior QST-557 SQL invoked that hook as postgres and therefore missed the effective-role boundary. This is a release blocker, not a proven explanation of any specific user's earlier login failure; the latest Hosted function and migration have not been deployed or tested together.

## Change

- Disable the Free-incompatible password-verification hook locally. Enable a Free-compatible Custom Access Token Hook that refuses token issuance for locked password logins while preserving recovery and token refresh.
- Grant the Auth execution role narrow table operations and add explicit SELECT/UPDATE RLS policies. Keep the hook as invoker; no broad `SECURITY DEFINER` hook was added.
- Add a rollback-only SQL contract that checks locked/unlocked/missing account behavior, recovery, refresh, and the `supabase_auth_admin` grants and RLS policies. The isolated CI database cannot switch its `postgres` connection into the reserved Auth role, so this contract does not prove execution under `supabase_auth_admin`.
- Send the Auth password grant with the public `apikey` header only, never a publishable key as a Bearer token. The Edge helper test now asserts the absence of that header. This is compatibility hardening, not a demonstrated explanation of the account owner's failed login.
- Correct the product authentication specification and migration manifests. The Hosted migration head remains old and the external Beta decision remains NO-GO.

## Hosted source comparison (2026-10-18)

- Read the deployed `auth-login` source from the Beta Dashboard ZIP. It is an older single-file implementation, not the local candidate: account lookup errors are collapsed into `invalid_credentials` (HTTP 401), whereas local source treats a failed lookup as service unavailability (HTTP 503). Thus a database lookup failure can be indistinguishable from a wrong ID/password to the user on Hosted.
- Hosted source still calls `record_auth_login_failure` and `record_auth_login_success`, not the local atomic `_v2` RPCs. The success RPC result is ignored. This is deployment drift, not proof that a specific attempt failed at either RPC.
- Hosted source sends the public key in both `apikey` and `Authorization: Bearer`. A single nonexistent test-only address with that header returned HTTP 400 from Supabase Auth; a separate nonexistent test-only address using only `apikey` also returned HTTP 400 with `error_code=invalid_credentials`. The header difference alone therefore did **not** reproduce the reported failure. No real account password was used or inspected.
- The first Dashboard Invocations read had not finished loading. The subsequent five-day result is summarized below; it has no per-user attribution. Do not infer the owner's password is wrong or that the login flow passed from these probes. The latest local implementation still needs an immutable candidate deployment and a consented real-account or disposable-account round trip.
