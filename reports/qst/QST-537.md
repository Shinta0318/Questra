# QST-537 Authoritative Mission Refresh After Remote Task Reopen

Status: In Progress / local_partial

## Problem and change

- A second device can reopen and re-complete a required Task while this device still holds an older Mission completion confirmation. Refreshing Tasks alone must not restore that old confirmation.
- The Task load and conflict-recovery paths now retrieve the corresponding Mission snapshots from the repository before applying a refreshed Task list. A missing or mismatched Mission snapshot fails the coupled refresh rather than treating stale local state as authoritative.
- When Mission refresh fails, the local confirmation is hidden and Mission completion is disabled until the user retries. An owner change or a newer load prevents an older response from applying. A previously started Mission list load cannot overwrite a newer coupled snapshot.

- Confirm the retry and stale-confirmation state on Web and Android at small widths and with accessibility settings. No live screen or Android evidence was collected for this QST.

Rollback: If coupled Mission refresh fails in a deployed build, keep the existing route read-only or retryable; do not fall back to a cached completion confirmation.
