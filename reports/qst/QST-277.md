# QST-277 Task Persistence Retry and Offline UX Report

## Result

Completed on 2026-08-08.

Task creation, batch creation and status changes now expose a consistent
saving, saved, failed or offline-pending state. A failed optimistic mutation is
rolled back on screen while its desired Task payload remains available for an
explicit retry during the active signed-in session.

## Changes

- Added a Task mutation state model with saving, saved, failed and
  offline-pending states.
- Added an in-session pending mutation boundary that retains the desired Task,
  previous Task and retry count.
- Applied optimistic Task updates and restored the previous UI state on save
  failure.
- Reused the same Task IDs and Supabase upsert path for retry idempotency.
- Added retry and recovery banners to Task list, Task detail and Mission detail.
- Kept failed mutations from being dismissed accidentally; authentication
  changes explicitly discard the previous user's pending data.
- Preserved existing Task availability and Mission progress derivation rules.

## Idempotency Boundary

- Creation retries reuse the original UUID, so an acknowledged-but-disconnected
  request cannot create a second Task.
- Status retries upsert the same resulting status.
- The hosted Task progress trigger records events only when status or schedule
  changes, so retrying an already-applied state does not duplicate its event.

## Operational Boundary

Pending mutation recovery is intentionally scoped to the active authenticated
session. Persisting offline writes across a full app termination requires an
encrypted device queue and conflict policy and should not store one user's
pending payload after sign-out.
