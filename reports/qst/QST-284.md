# QST-284 Arc Task Context Integration

## Result

Completed on 2026-08-08. Arc Chat now receives a bounded, owner-scoped view of
open Tasks and keeps Mission outcomes separate from Task actions in both the
Flutter client and the hosted Gemini prompt.

## Implementation

- Added up to five focused or recent open Tasks to `ArcChatContext`.
- Scoped Tasks to the focused Mission, focused Quest, or active Quest set.
- Prioritized in-progress and dependency-ready Tasks before pending work.
- Included Task action, completion condition, dependency IDs, and parent IDs.
- Updated the local Arc fallback to name the next Task and its done condition.
- Updated the Edge Function prompt so Mission means a verifiable checkpoint and
  Task means the smallest concrete action.
- Removed the explicit Arc Chat sampling temperature from the current Gemini
  contract.
- Added non-sensitive context usage metadata for deterministic hosted evidence.
- Extended the two-account acceptance runner and strict verifier with the hosted
  Arc Task context check.

## Safety And Data Boundaries

- The Flutter client only sends Tasks already loaded for the signed-in owner.
- Context is bounded to five open Tasks; completed Tasks are not re-proposed.
- The hosted acceptance uses an owner Task and verifies the focused Task ID.
- Evidence records only pass/fail metadata and generated IDs, not journey text,
  account email addresses, access tokens, API keys, or private Arc responses.
- Gemini still has no direct database access and all writes remain outside this
  read-only chat context.
