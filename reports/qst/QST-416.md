# QST-416 Height-Aware Navigation and Escape Routes

更新日: 2026-09-05 / 状態: InProgress（実装・Widget検証済み、Web/Android実画面証跡は残件）

## 原因

`AppShell`は画面幅だけでNavigation Railを選択していたため、844x390のような横長・低い画面でも先頭ロゴと5 destinationを縦配置し、overflowし得た。Bottom Navigationの`プロフィール`は狭い幅で省略され、文字拡大に応じた高さもなかった。未知Routeには専用画面がなく、Guild Pilot未接続と共有Trailの無効リンクには、安全なHome/Questへの回復CTAが不足していた。

## 実装

- `NAVIGATION_HEIGHT_AWARE_V2`を追加。利用可能高さが600未満ならRailからBottom Navigationへ切り替える。
- `viewInsets.bottom`を利用可能高さから差し引き、キーボードで560未満になった場合はNavigationを一時非表示にして本文と入力を保護。
- Bottom Navigationの高さをtext scalerへ追従させ、Reduce Motion時は選択animationを0msにする。
- プロフィールの視覚ラベルを`自分`へ短縮し、Semantics/Tooltipは正式名`プロフィール`を維持。
- GoRouterへ`RouteRecoveryScreen`を追加。未知RouteからHomeまたはQuestへ移動でき、保存データを変更しないことを明示。
- GuildのAppBarに戻る/ホーム操作、Pilot gateに`Questへ戻る`、読込失敗に`ホームへ戻る`を追加。
- 共有TrailのAppBarに戻る/ホーム操作を追加し、無効・期限切れ・rate limit状態に`Questraを開く`を追加。

専用テストでは844x390のBottom Navigation、360x800/文字2倍の表示名とSemantics、390x800/keyboard inset 300のNavigation退避、未知RouteのHome/Quest回復、Guild gate、無効共有Trailを確認した。

PR #19のRelease Gateで、`flutter pub get`とテストが生成した5件をcandidateのdirty stateと誤判定した。クリーン判定を生成処理より前へ移動し、PRのdetached checkoutでは`GITHUB_HEAD_REF`を検証対象ブランチとして利用するよう修正した。dirty判定時は対象パスも出力するため、今後は件数だけで原因が隠れない。

CI修正後の局所検証は、Workflow順序3 tests、candidate Git状態10 scenarios、Flutter/Dart analyze、対象差分checkがすべてPASSした。GitHub上の最終判定は修正commit後のRelease Gateへ委ねる。

再実行ではsource preflight、全763 tests、Core journey、Web E2Eが通過し、未承認Arc asset snapshotの古いsource commitを通常CIでも最新HEAD必須としていた次の不整合を検出した。Asset/依存関係の通常ゲートはsource commit形式と現在のhash/inventoryを検証し、正式配布ゲートだけが最新HEAD一致と人間承認を要求するよう責務を分離した。

同じ原則をExternal Beta判断にも適用した。`NO_GO`は未完了ゲートと有効な評価元SHAを検証し、配布可能な`GO`だけが現在HEADとの一致を必須とする。コード変更のたびに未実施の外部証跡を再生成する運用は採用しない。

## 未確認・残余リスク

- 実Web/Androidでの横画面、ソフトウェアキーボード表示・復帰、OS戻る連打、SafeArea、browser historyは未確認。
- 390x844、430x932、768x1024、1280x800、英語最大長、文字1.3倍の全matrixは今回の専用テスト外。
- キーボード中は狭いNavigationを一時非表示にする。入力中にもdestinationを常時表示する要件が生じた場合は、本文領域と合わせた別設計が必要。
- `自分`は幅不足を解消する暫定的な日本語表示名。ユーザー検証は未実施。
- Settings/Data Rights/Arc Memory/Feedbackなど他の独立RouteのAppBar・履歴なしdeep link回復はQST-413/415と合わせた全Route監査が残る。
- 未知Routeの回復先は認証状態に応じて既存Auth GuardがLogin/Onboardingへredirectする。未認証実ブラウザー証跡は未取得。
