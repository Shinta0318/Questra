## Finding

The connected Web preview requested recovery in one browser, while the mail link was opened in another. The previous Web recovery client used PKCE; its verifier is kept in the requesting browser. The reset screen nevertheless displayed password fields before any recovery session existed. A visible reset form was therefore mistaken for a validated link. Supabase confirmed an account, email verification, and recent failed login attempts, but does not expose or prove the saved password. No successful reset or subsequent login has been observed.

## Local change

- Web recovery requests use an isolated implicit-flow client and the current Origin's `/?auth_callback=recovery`. Mobile keeps PKCE; already-issued Web `/#/reset-password` links retain the legacy SDK exchange path.
- Startup accepts only a complete `type=recovery` callback, scrubs tokens from the browser URL before Supabase initialization, and validates the session through Supabase before entering the password form.
- An unverified or expired callback displays recovery guidance and a resend action without password fields.
- Password update success is now distinct from login-lock cleanup and sign-out. If either post-update step fails, the UI does not claim that the password was unchanged or ask the user to submit it again. Sign-out can be retried without repeating the password update; a failed lock-clear is disclosed at login.
- The redirect release gate expects the dedicated recovery URL and tolerates the old exact Web path during transition. It does not allow wildcard URLs.
- The local Supabase redirect list includes the dedicated recovery callback for configured localhost and 127.0.0.1 preview ports. This does not change Hosted Beta settings.

## Residual risk and rollback

QST-579's full-suite regression found two older QST-548/551 tests that expected reset inputs without a verified recovery session. Their fixtures now provide that session for contrast and validation checks. The invalid-link test still proves that unverified sessions show no password fields. Focused recovery tests and the final 1,162-pass Flutter suite succeeded; production reset behavior was not relaxed.

The default Supabase confirmation email link transports a short-lived session in the browser URL. The app strips it before SDK startup, but mail clients and browser history may briefly contain it; the link must not be shared. The legacy PKCE path still requires its original browser and may fail. Web uses `EmptyLocalStorage`, so a reload after password update but before a failed sign-out retry discards the in-memory recovery session and pending UI state. The user should then use the new password to log in; this behavior still needs a real-mailbox test. No token persistence was added to solve a status-display problem. A source rollback should restore the previous Web request route while keeping the old exact redirect until outstanding emails expire; remove the new redirect only after no links depend on it. External Beta stays NO-GO until a same-candidate real mailbox round trip and QST-552 profile login succeed.
